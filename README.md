# Система формування рапортів про використання БпЛА та боєприпасів

Настільний застосунок (C# / .NET 8 / WPF) для зведення поданих оператором
епізодів у готовий рапорт у форматі Word. Дані надходять із Google-форми
через привʼязану таблицю або з демонстраційного джерела.

Наскрізний проєкт для лабораторних робіт з дисципліни
**«Конструювання програмного забезпечення»** (ХНУ).

---

## Швидкий старт

```bash
dotnet build ReportsWpf.sln
```

```bash
dotnet run --project src/Reports.Wpf/Reports.Wpf.csproj
```

Перший запуск сам створює базу з довідниками-прикладами і шаблон рапорту.
Застосунок одразу працює на **демонстраційних даних** — без Google та інтернету.

Далі: вкладка **«Відповіді» → «Синхронізувати»**, потім
**«Формування рапорту» → «Переглянути текст» → «Створити документ»**.

### Перевірка працездатності

```bash
dotnet run --project tests/Reports.SmokeTest/Reports.SmokeTest.csproj
```

Наскрізний тест: база → імпорт → дедуплікація → зведення → `.docx` → журнал.
Виводить перелік перевірок і код повернення 0/1.

### Лабораторна робота №8 (окремо від застосунку)

```bash
dotnet run --project lab8/TranslatorTables/TranslatorTables.csproj
```

## Структура рішення

| Проєкт | Призначення |
|---|---|
| `src/Reports.Core` | Предметна область: сутності, періоди, правила агрегації, служби. Без UI та БД |
| `src/Reports.Data` | Entity Framework Core + SQLite: контекст, репозиторії, наповнення |
| `src/Reports.Documents` | Формування `.docx` через OpenXML: шаблон і заміна тегів |
| `src/Reports.Integration` | Google Sheets API, OAuth, демонстраційне джерело даних |
| `src/Reports.Wpf` | Інтерфейс WPF за схемою MVVM |
| `tests/Reports.SmokeTest` | Наскрізна перевірка ланцюга |
| `lab8/TranslatorTables` | Таблиці транслятора з мови СІ — окрема програма |
| `docs/` | Тека для звітів і документів лабораторних робіт |

## Підключення Google (необовʼязково)

Застосунок працює й без цього — на демонстраційних даних.

1. [Google Cloud Console](https://console.cloud.google.com) → новий проєкт.
2. **APIs & Services → Library** → увімкнути **Google Sheets API**.
3. **OAuth consent screen** → External → додати свій акаунт у **Test users**
   (це прибирає попередження «застосунок не перевірено»).
4. **Credentials → Create credentials → OAuth client ID** → тип **Desktop app**
   → Download JSON.
5. Покласти файл як `%AppData%\Рапорти\credentials.json`.
6. У застосунку: **«Налаштування»** → зняти галочку «Демонстраційні дані»,
   вставити **ідентифікатор таблиці** з її адреси
   (`docs.google.com/spreadsheets/d/`**`ІДЕНТИФІКАТОР`**`/edit`) → **«Зберегти»**.
7. **«Відповіді» → «Синхронізувати»** — відкриється браузер із запитом згоди.

Усе безкоштовно: проєкт Google Cloud, Sheets API і квоти для цього обсягу
плати не потребують.

### Як читається таблиця

- **`Довідники`** — чотири блоки поруч: `A|B` БпЛА, `D|E` Цілі, `G|H` Боєприпаси,
  `J|K` Місця; дані з рядка 3. Ліва колонка — як у формі, права — як у рапорті
  (для цілей — **родовий відмінок**, для місць — область).
- **`Люди`** — `Email | ПІБ | Звання | Посада`, дані з рядка 2.
- **`Відповіді`** — колонки шукаються **за заголовками**, а не за номерами,
  тому питання у формі можна переставляти. Колонка `Статус` зі значенням
  `СКАСОВАНО` виключає запис із рапорту назавжди.

## Шаблон рапорту

`template.docx` — звичайний документ Word із тегами. Програма не знає нічого
про оформлення, вона лише замінює теги, тож шаблон можна вільно переверстувати.

| Тег | Значення |
|---|---|
| `{{ДАТА_З}}`, `{{ДАТА_ПО}}` | межі періоду, ДД.ММ.РРРР |
| `{{ТИП_ТА_КІЛЬКІСТЬ_БПЛА}}` | типи БпЛА з сумарною кількістю, за спаданням |
| `{{БОЄПРИПАСИ}}` | унікальні повні назви через кому |
| `{{ТИП_ЦІЛІ}}` | унікальні повні назви, родовий відмінок |
| `{{ПІДРОЗДІЛ}}` | назва підрозділу з налаштувань |
| `{{НАСЕЛЕНИЙ_ПУНКТ}}`, `{{ОБЛАСТЬ}}` | місця періоду й області з довідника |
| `{{НАКАЗ}}` | бойовий наказ із вікна формування |
| `{{ПОСАДА}}`, `{{ЗВАННЯ}}`, `{{ПІБ}}` | підписант із довідника «Люди» |

Гриф, адресат і резолюція вписані в шаблон при його створенні.
Після зміни в налаштуваннях — меню **«Шаблон → Перебудувати за налаштуваннями»**.

## Відповідність лабораторним роботам

| № | Тема | Що взяти з проєкту |
|---|---|---|
| 1 | Технічне завдання | Предметна область, склад функцій, вимоги до технічних засобів і сумісності |
| 2 | Ескізний проект | ERD — схема БД у `AppDbContext`; DFD — потік «форма → таблиця → імпорт → зведення → документ»; STD — стани запису (`RecordStatus`); словник термінів |
| 3 | Технічний проект | Структурна схема — розподіл на 5 проєктів; функціональна схема; карти Константайна за графом залежностей; специфікації модулів — XML-коментарі |
| 4 | Реалізація | Сам застосунок + документація; скріншоти всіх вкладок; лістинги ключових модулів |
| 5 | LOC- і FP-метрики | LOC рахувати по `src/`; для FP: зовнішні введення — форми довідників, виведення — `.docx` і журнал, запити — прев'ю й фільтри, внутрішні файли — таблиці SQLite, **зовнішній інтерфейсний файл — Google Sheet** |
| 6 | COCOMO II | Розмір із лабораторної 5; фактори витрат за своїм варіантом |
| 7 | ОО-метрики | Ієрархії `Entity → ReferenceItem → 4 нащадки`, `PeriodPreset → 6 нащадків`, `AggregationRule → 11 правил`, `SymbolTableBase → 5 таблиць`. Є що міряти для DIT, NOC, WMC, CBO, RFC, LCOM |
| 8 | Таблиці транслятора | `lab8/TranslatorTables` — усі 6 таблиць мови СІ, 5 способів організації, 5 хеш-функцій, тестові дані й порівняння |

## Технології

DocumentFormat.OpenXml 3.1 · Google Sheets API v4 (OAuth 2.0, Desktop app)

не залежала від фідів, прописаних на конкретній машині.
